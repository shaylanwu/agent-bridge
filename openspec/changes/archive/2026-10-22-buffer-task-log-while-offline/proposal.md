## Why

`bridge-client.ts` 的 `send()` 对断线期间的消息做了区别对待：控制类消息进队列，而 `task_log` 直接 `return` ——
**丢弃**（注释写着"避免内存膨胀"）。这条取舍在长时间任务上会出事：

- 编码 Agent 跑十几分钟，中间输出几千行；网络抖动 30 秒（或平台侧重启），这 30 秒的输出永久消失；
- 平台侧看到的是"日志突然接不上了"，而且**没有任何标记**说明中间缺了内容 —— 排障时会被当成模型没输出；
- 任务本身没受影响（进程还在跑、`task_status` 最后也会到），所以问题很隐蔽。

反面也不能走极端：断线一小时还无脑缓存，会把 bridge 进程撑爆。

## What Changes

- 新增 `src/outbox.ts`：断线期间的有界发送缓冲区
  - **控制类消息**（`agent_list` / `scan_progress` / `scan_result` / `task_status`）单独一条队列（上限 200 条，满了丢最旧）；
  - **日志**（`task_log`）单独按**字节**计上限（默认 256 KB），满了丢**最旧**的（保留最近的上下文，排障时更有用），并累计丢弃量；
  - `drain()` 按「先控制、后日志」返回待发列表；若有丢弃，在日志前插入一条**说明性 `task_log`**
    （挂在被缓冲的第一条日志的 `taskId` 上）：`[agent-bridge] 断线期间日志超出缓冲上限（N KB），已丢弃较早部分`。
- `bridge-client.ts`：`queue` 换成 `Outbox`，重连 `flush()` 走 `drain()`。
- 文档：两份 README 的协议/行为说明补一段「断线期间的日志会被缓冲并补发，超限时带截断提示」。

协议**无字段变更**（消息类型与形状不变，只是断线期间不再丢），`PROTOCOL_VERSION` 不变。

## Impact

- 协议：无变更（`task_log` 补发会带原来的 `taskId`，顺序保持）
- CLI：无新增命令/参数；新增内部模块 `src/outbox.ts`
- 适配器：无
- 内存：断线期间最多额外占用约 256 KB（日志）+ 少量控制消息
- 文档：两份 README
- 风险级别：medium（`bridge-client` + 新模块，不动协议字段与 spawn 边界）
