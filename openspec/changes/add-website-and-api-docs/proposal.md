# 变更提案：官网 + 功能 API 对接文档（含版本历史自动更新）

## Why

本包要被**任意外部系统**接入（当前只有 e2e-pilot，未来要有 IDE 插件、CI、第三方编排器）。
今天第三方能拿到的全部信息是两份 README 的中文/英文散文 —— 没有可检索站点、没有机器可读的接口契约、
没有版本历史，接入成本全靠人肉问答。这与"开放性/扩展性"的目标直接冲突。

## What Changes

在**本包内独立**增加一个文档站点（`site/`），以及随发布自动更新的版本历史：

- 官网：产品首页 + 快速上手 + CLI 参考 + 架构说明 + 协议说明 + **API 对接文档** + 版本历史；
- API 文档：以 **AsyncAPI 3.0**（WS 通道）+ **OpenAPI 3.1**（平台需实现的 HTTP 端点）+
  **OpenAPI 3.1**（本地回环控制面，2026-10-23 落地）为**唯一真源**，站点渲染成可交互参考页；
- 读者分叉：站点按「**平台方**」与「**本机程序作者**」两条对接路径组织（控制面落地后新增的第二类读者）；
- 版本历史：由发布流水线自动生成，站点构建时读取，无需手工维护；
- 独立性：`site/` 拥有自己的 `package.json` 与锁文件，**不进主包 `files`、不污染主包运行时依赖
  （主包仍只有 `ws` + `smol-toml`）**。

## Impact

- 主包（`agent-bridge-service`）的 npm 产物与运行时依赖**不变**；站点是仓库内的独立工作区。
- 新增开发期依赖只在 `site/` 下；主包 `package.json` 只新增 `site:*` 脚本与 `semantic-release` 相关 devDependencies。
- 发布流程改为自动化（Conventional Commits → 版本号 → CHANGELOG → tag → npm），需要 `NPM_TOKEN` 配置一次。
- 站点内容必须与代码同源：协议类型 / 能力清单 / **CLI 命令（6 个）** / **控制面端点（9 个路径）**
  已有 CI 校验（`doc-contract-check`），站点侧再补两条渲染前校验。
